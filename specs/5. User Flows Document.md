# 1. Purpose

This document defines the main user flows for the Wireless Connect Online Store. It should be used by Claude Code/Codex to build pages, components, server actions, validation, redirects, empty states, loading states, and error handling.

The goal is to make the shopping experience simple, trustworthy, and optimized for selling used phones online.

---

# 2. User Types

## Guest Customer

A visitor who is not signed in.

Can:

- Browse products
- Search products
- Filter products
- View product details
- Add items to cart
- Checkout as guest
- Choose local pickup or shipping

## Registered Customer

A signed-in customer.

Can:

- Do everything a guest can do
- Save addresses
- View order history
- Manage profile
- Track order status

## Staff

A store employee.

Can:

- Access admin dashboard
- Manage products
- Manage orders
- Update inventory
- Mark orders ready for pickup

## Admin

Business owner or manager.

Can:

- Do everything staff can do
- Manage staff access
- Manage global settings
- View private product fields

---

# 3. Global UX Rules Across All Flows

1. Every flow must be mobile-first.
2. Every flow must include loading states.
3. Every flow must include empty states where applicable.
4. Every write action must validate user input.
5. Every important action must show clear success or error feedback.
6. Checkout-related actions must revalidate product inventory server-side.
7. Admin actions must require staff/admin permissions.
8. Public customers must never see IMEI, serial number, product cost, or admin notes.
9. Customers must always see trust signals when buying a used device.
10. Users should never reach a dead end; every empty/error state should include a next action.

# 24. Stripe Payment Flow

## Goal

Payment is handled safely and order status updates correctly.

## Flow

```text
Customer clicks Continue to Payment
→ Server validates checkout
→ Pending order created
→ Stripe Checkout Session created
→ Customer pays on Stripe
→ Stripe sends webhook
→ Webhook verifies signature
→ Order marked paid
→ Inventory decremented
→ Confirmation email sent
→ Customer returns to confirmation page
```

## Failure Flow

```text
Customer abandons Stripe Checkout
→ Order remains pending/unpaid
→ Inventory not decremented
→ Cart remains available
```

## Payment Failed Flow

```text
Stripe payment fails
→ Order payment_status = failed
→ Inventory not decremented
→ Customer can retry checkout
```

## Critical Rule

Inventory must decrement only after confirmed payment webhook.

# 29. Edge Cases

## Product Sold While in Cart

Customer sees:

```text
This item is no longer available.
```

Required action:

- Disable checkout until item is removed.

## Price Changes While in Cart

Customer sees:

```text
The price of one item has changed. Please review your cart before checkout.
```

## Stripe Webhook Repeated

System should:

- Detect order already paid.
- Avoid duplicate inventory decrement.
- Avoid duplicate confirmation email if possible.

## Guest Loses Cart Cookie

Customer sees empty cart.

No account recovery required for MVP.

## Admin Archives Product in Active Cart

Checkout validation should block purchase.

## Customer Refreshes Confirmation Page

Confirmation page should still load order summary safely.

## Email Fails

Order should remain successful.

System should log email failure.

# 31. Acceptance Criteria

The user flows are complete when:

1. A guest can browse products.
2. A guest can search/filter products.
3. A guest can view product detail pages.
4. A guest can add an active in-stock product to cart.
5. A guest can remove/update cart items.
6. A guest can checkout using Stripe.
7. A successful Stripe payment marks an order paid.
8. Inventory decrements only after payment success.
9. A customer can receive an order confirmation.
10. A staff/admin user can sign in to admin.
11. A staff/admin user can create and edit products.
12. A staff/admin user can upload product images.
13. A staff/admin user can view orders.
14. A staff/admin user can update order status.
15. Public users cannot access admin routes.
16. Public users cannot see IMEI, serial number, product cost, or admin notes.
17. Every empty state has a useful CTA.
18. Every critical error has a clear recovery path.
19. The UI remains mobile-friendly across all flows.
20. Future repair/trade-in flows are documented but not required for MVP.
