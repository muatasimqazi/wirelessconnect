# 1. Purpose

This document defines the main user flows for the Wireless Connect Online Store. It should be used by Claude Code/Codex to build pages, components, server actions, validation, redirects, empty states, loading states, and error handling.

The goal is to make the shopping experience simple, trustworthy, and optimized for selling used phones online.

---

# 2. User Types

## Guest Customer

A visitor who is not signed in.

Can:

- Browse products
- Search products
- Filter products
- View product details
- Add items to cart
- Checkout as guest
- Choose local pickup or shipping

## Registered Customer

A signed-in customer.

Can:

- Do everything a guest can do
- Save addresses
- View order history
- Manage profile
- Track order status
- Submit warranty claims
- Request order cancellation

## Guest Customer (Post-Purchase)

A guest with a `guest_access_token` from their order confirmation email.

Can:

- View their specific order via `/order-confirmation?token={{guestAccessToken}}`
- Access is scoped to the single order linked to the token

## Staff

A store employee.

Can:

- Access admin dashboard
- Manage products
- Manage orders
- Update inventory
- Mark orders ready for pickup

## Admin

Business owner or manager.

Can:

- Do everything staff can do
- Manage staff access
- Manage global settings
- View private product fields

# 3. Global UX Rules Across All Flows

1. Every flow must be mobile-first.
2. Every flow must include loading states.
3. Every flow must include empty states where applicable.
4. Every write action must validate user input.
5. Every important action must show clear success or error feedback.
6. Checkout-related actions must revalidate product inventory server-side.
7. Admin actions must require staff/admin permissions.
8. Public customers must never see IMEI, serial number, product cost, or admin notes.
9. Customers must always see trust signals when buying a used device.
10. Users should never reach a dead end; every empty/error state should include a next action.

```ts
const { data: order } = await supabase
  .from('orders')
  .select('...')
  .eq('guest_access_token', token)
  .single()
```

# 24. Stripe Payment Flow

## Goal

Payment is handled safely and order status updates correctly.

## Flow

```text
Customer clicks Continue to Payment
→ Server validates checkout
→ Pending order created
→ Stripe Checkout Session created
→ Customer pays on Stripe
→ Stripe sends webhook
→ Webhook verifies signature
→ Order marked paid
→ Inventory decremented
→ Confirmation email sent
→ Customer returns to confirmation page
```

## Failure Flow

```text
Customer abandons Stripe Checkout
→ Order remains pending/unpaid
→ Inventory not decremented
→ Cart remains available
```

## Payment Failed Flow

```text
Stripe payment fails
→ Order payment_status = failed
→ Inventory not decremented
→ Customer can retry checkout
```

## Webhook Idempotency

The webhook handler must check for duplicate processing using the `webhook_events` table:

```sql
INSERT INTO webhook_events (stripe_event_id, event_type, payload)
VALUES ($1, $2, $3)
ON CONFLICT (stripe_event_id) DO NOTHING
RETURNING id
```

If no row is returned, the event was already processed — skip remaining logic.

## Critical Rule

Inventory must decrement only after confirmed payment webhook.

# 29. Customer Flow: Guest Order Lookup

## Goal

Guest customer views their order using a secure token from their confirmation email — without creating an account.

## Entry Points

- Order confirmation email CTA ("View Order" link)
- Direct URL with token

## Flow

```text
Receive order confirmation email
→ Click "View Order" button
→ Browser loads /[locale]/order-confirmation?token={{guestAccessToken}}
→ Server fetches order by guest_access_token UUID
→ Display order summary
```

## Security Rules

- Access token is a UUID (`gen_random_uuid()`)
- Token is not the order number — prevents IDOR
- Token is per-order, not per-customer
- No authentication required
- If token is invalid or not found, show 404 (not an error message that confirms the order exists)

## Success State

Display order summary:

- Order number
- Order date
- Items ordered
- Fulfillment method (pickup or shipping)
- Order status
- Tracking number (if shipped)
- 30-day warranty reminder

## Error / Not Found State

```text
Order not found.
```

CTA:

```text
Return to Store
```

Do NOT expose whether the order number exists. Respond with a generic not-found message.

Customer reports a defect and requests warranty service within 30 days of purchase.

## Entry Points

- `/account/warranty-claims` — registered customers
- `/order-confirmation?token=...` — guest customers (link from order detail)

## Flow (Registered)

```text
Account
→ Warranty Claims
→ Select order / product
→ Describe issue
→ Upload photos (optional)
→ Submit claim
→ Claim created with status "Under Review"
→ Warranty claim received email sent to customer
→ Admin notified
```

## Flow (Guest)

```text
Order confirmation page (via token URL)
→ "Submit Warranty Claim" link
→ Claim form with order pre-filled
→ Enter contact info (since guest has no account)
→ Describe issue
→ Submit claim
→ Warranty claim received email sent
```

## Required Fields

- Product (from order)
- Issue description (text)
- Photos (optional)

## Eligibility Check

Server must verify:

- The order exists
- The order is within the 30-day warranty window from `created_at`
- The order status is not `cancelled` or `refunded`
- No existing active claim for the same product on the same order

## Success State


## Error States

# 34. Admin Flow: Device Intake (with Hold Period)

## Goal

Staff records a used device purchased from a seller, capturing seller identity for RCW 19.60 compliance.

## Entry Point

```text
/admin/intake/new
```

## Flow

```text
Admin dashboard
→ Intake
→ New Intake
→ Enter device details (brand, model, storage, IMEI, serial number)
→ Enter seller identity section (required for Washington State compliance)
→ Record acquisition details (price paid, payment method)
→ Set hold period (minimum 5 days per RCW 19.60)
→ Save intake record
→ Device status: "hold_period"
→ After hold_until_date passes, status may advance to "in_testing"
```

## Seller Identity Required Fields

- Seller full name
- Seller phone
- Seller ID type (driver_license, state_id, passport, military_id, other)
- Seller ID number (encrypted at rest — never stored in plaintext)
- Seller ID state
- Seller ID expiry
- Seller address
- Seller declaration signed (boolean — customer signs agreeing device is theirs)

## Hold Period UI Requirements

- Display `HoldPeriodBadge` on intake detail page
- Show `hold_until_date` prominently
- Show remaining days until hold expires
- Block "Convert to Product" and "Ready to List" actions until hold period has passed
- Display warning: "Device is in hold period — cannot be listed for sale until [date]"

## Hold Period Statuses

```text
hold_period → in_testing → tested → ready_to_list → listed
```

## Publishing Gate

The `PublishingGateStatus` component must display before allowing device to be listed:

```text
✓ IMEI verified
✓ Battery health recorded
✓ All test checklist items passed
✓ Hold period expired
✓ At least one product image uploaded
✓ Price set (> 0)
✓ Seller declaration signed
✓ Acquisition cost recorded
✓ No outstanding flags
✓ Device graded
```

All 10 gates must pass before the "Convert to Product" button is enabled.

# 35. Edge Cases

## Product Sold While in Cart

Customer sees:

```text
This item is no longer available.
```

Required action:

- Disable checkout until item is removed.

## Price Changes While in Cart

Customer sees:

```text
The price of one item has changed. Please review your cart before checkout.
```

## Stripe Webhook Repeated

System should:

- Detect order already paid.
- Avoid duplicate inventory decrement.
- Avoid duplicate confirmation email if possible.

## Guest Loses Cart Cookie

Customer sees empty cart.

No account recovery required for MVP.

## Admin Archives Product in Active Cart

Checkout validation should block purchase.

## Customer Refreshes Confirmation Page

Confirmation page should still load order summary safely.

## Email Fails

Order should remain successful.

System should log email failure.

# 37. Acceptance Criteria

The user flows are complete when:

1. A guest can browse products.
2. A guest can search/filter products.
3. A guest can view product detail pages with breadcrumb navigation.
4. A guest can add an active in-stock product to cart.
5. A guest can remove/update cart items.
6. A guest can checkout using Stripe with automatic tax calculation.
7. A successful Stripe payment marks an order paid.
8. Inventory decrements only after confirmed payment webhook (atomic, oversell-safe).
9. Webhook idempotency prevents duplicate order processing.
10. A guest receives an order confirmation email with a `guest_access_token` link.
11. A guest can view their order via `/order-confirmation?token=<uuid>` — not via order number.
12. A registered customer can view and manage orders in their account.
13. A customer can submit a warranty claim within 30 days of purchase.
14. A customer can request order cancellation when order is in eligible status.
15. A customer can submit a CCPA data deletion request from the footer.
16. A staff/admin user can sign in to admin.
17. A staff/admin user can create a device intake record with seller identity fields.
18. Hold period is enforced — devices cannot be listed until `hold_until_date` passes.
19. All 10 publishing gate checks pass before a device can be converted to a product.
20. A staff/admin user can create and edit products.
21. A staff/admin user can upload product images.
22. A staff/admin user can view and update orders.
23. Admin must enter tracking number and carrier before marking an order Shipped.
24. Admin can manage warranty claims (Under Review → Approved → Resolved / Denied).
25. Warranty claim status update email is sent to customer in their locale.
26. Order cancelled email is sent when admin cancels an order.
27. Public users cannot access admin routes.
28. Public users cannot see IMEI, serial number, product cost, or admin notes.
29. Every empty state has a useful CTA.
30. Every critical error has a clear recovery path.
31. The UI remains mobile-friendly across all flows.
32. Future repair/trade-in flows are documented but not required for MVP.
