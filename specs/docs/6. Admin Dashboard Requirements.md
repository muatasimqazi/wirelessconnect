# 1. Purpose

This document defines the admin dashboard requirements for the Wireless Connect Online Store.

The admin dashboard allows Wireless Connect staff to manage online inventory, product intake, device testing, IMEI verification, product images, orders, coupons, warranties, and store settings.

The dashboard should be simple, fast, and focused on daily store operations. It should not feel like enterprise software.

---

# 2. Admin Dashboard Goals

## Business Goals

1. Allow staff to list used phones quickly.
2. Allow staff to manage available inventory accurately.
3. Allow staff to process online orders.
4. Allow staff to update local pickup and shipping statuses.
5. Allow staff to manage discounts and store settings.
6. Prevent accidental exposure of private product/customer data.
7. Standardize used-device intake, testing, grading, and publishing.
8. Ensure devices are activation-ready before being listed online.
9. Track warranty and fulfillment status clearly.
10. Support English/default product content and Spanish storefront content where available.

## UX Goals

1. Mobile-friendly, but optimized for desktop/tablet use.
2. Minimal clicks for adding a product.
3. Clear order status management.
4. Fast product search and filtering.
5. Clear success/error messages.
6. No confusing technical language.
7. Make device intake fast and checklist-driven.
8. Reduce mistakes when entering IMEI, battery health, condition, and warranty data.
9. Keep admin UI English-only for MVP while allowing staff to enter localized storefront content.

# 7. Device Intake Management

Base routes:

```text
/admin/intakes            — list all intakes
/admin/intakes/new        — individual purchase intake (RCW 19.60 compliant)
/admin/intakes/wholesale  — wholesale batch intake (no seller identity required)
/admin/intakes/[id]       — intake detail / workflow
```

## Purpose

Provide a checklist-driven workflow for preparing used devices before they are listed online.

Used phones should not be published until intake, testing, IMEI verification, grading, photos, and pricing are complete.

## Two Intake Types

### Individual Purchase (`/admin/intakes/new`)
For devices purchased directly from private individuals. RCW 19.60 compliance required:
- Seller full identity (name, phone, email, address)
- Government ID type, number (encrypted), state, expiry
- Seller declaration signature
- Hold period enforced (minimum 3 days, default)

**IMEI Scanner**: Scan IMEI with Zebra scanner to auto-fill brand, model, storage, color, serial number, and blacklist status via IMEICheck.com API.

### Wholesale Batch (`/admin/intakes/wholesale`)
For devices purchased from licensed wholesale suppliers. RCW 19.60 individual hold period not required.
- Supplier info entered once (name, invoice #, date, payment method)
- Per-unit cost default with per-device override
- Staff scans IMEIs back-to-back (auto-refocus on input)
- IMEI Lookup toggle: ON (calls IMEICheck API) / OFF (free local Luhn check only)
- Hold period auto-waived for wholesale purchases
- Blacklisted devices allowed (intaked for parts/review with status = "failed")
- All device fields editable inline in batch table
- Single submit creates all intake records

# 7.2 Intake Form

Route:

## Required Sections

### Device Identity

### Seller Identity (Required for Individual Purchases — RCW 19.60 Compliance)

This section is required for all devices purchased from individuals. It is not required for documented wholesale supplier purchases, donations, or other non-individual acquisition sources. Washington State law (RCW 19.60) requires secondhand dealers to record seller identity for individual seller purchases.

Fields:

- Seller full name (required)
- Seller phone number
- Seller email address
- Seller ID type (required): driver_license, state_id, passport, military_id, other
- Seller ID number (required — stored encrypted using `pgp_sym_encrypt`, never in plaintext)
- Seller ID issuing state (required for driver_license and state_id)
- Seller ID expiry date
- Seller home address (required)
- Seller declaration signed (checkbox — seller attests the device is theirs to sell)
- Seller declaration signed timestamp (auto-set when checkbox is checked)

**Security requirement:** The seller ID number must be encrypted before storage using `pgp_sym_encrypt(id_number, SELLER_ID_ENCRYPTION_KEY)`. It must never be stored in plaintext, logged, or returned in API responses.

### Hold Period (Required — RCW 19.60 Compliance)

Fields:

- Hold start date (auto-set to acquisition date)
- Hold period days (default: 5 — minimum per RCW 19.60)
- Hold until date (auto-calculated: start date + hold_period_days)
- Hold period waived (boolean — for authorized exceptions only, requires admin role)

**UI Requirement:**

- Display `HoldPeriodBadge` prominently on intake detail page
- Show days remaining: "Hold expires in 3 days" / "Hold expired — device may be listed"
- Block all publishing-related actions (Ready to List, Convert to Product) until hold has passed
- If admin attempts to advance status before hold expires, show error:

```text
This device is in a hold period until [date]. It cannot be listed for sale until then.
```

### Source Information

Fields:

- Acquisition source (`individual_purchase`, `wholesale_supplier`, `trade_in`, `consignment`, `donation`, `other`)
- Acquisition date (required)
- Cost (required — acquisition price paid to seller)
- Acquisition payment method (cash, check, store_credit, zelle, venmo, other)
- Supplier/customer notes

### IMEI Verification

Fields:

- Clean IMEI status
- Not blacklisted
- Not financed
- Activation lock removed
- Verification date
- Verified by (staff name)
- IMEI verification service used (e.g., IMEI Pro, Swappa, Unlock River, carrier check)
- Verification notes

- IMEI verification status (pending, passed, failed)

Note: The IMEI verification service name (`imei_verification_service`) must be recorded so compliance reports can document the verification method used.

### Testing Checklist

Fields:

- Power on
- Touchscreen
- Face ID / Touch ID
- Cameras
- Speakers
- Microphone
- Charging port
- Wireless charging
- Bluetooth
- WiFi
- Cellular
- Buttons
- Battery health
- Battery cycle count optional
- Factory reset verified
- Data wiped verified

### Condition & Grading

Fields:

- Condition grade
- Cosmetic notes
- Functional notes
- Defect disclosure
- Included accessories

### Photos

Fields/features:

- Upload required photos
- Battery health photo
- Imperfection photos when needed
- Localized alt text when available

- Internal-only image flag

### Pricing & Publishing Prep

Fields:

- Price
- Compare-at price
- Warranty days
- Allow pickup
- Allow shipping
- Featured candidate

## Publishing Gate

A used phone cannot be converted to an active product unless all 15 canonical gates pass:

1. ✓ IMEI verified (verification status = passed)
2. ✓ Battery health recorded (0–100)
3. ✓ All testing checklist items passed
4. ✓ Hold period expired (`hold_until_date` is null or in the past)
5. ✓ At least 6 customer-facing product images selected for publication
6. ✓ Price set (> 0)
7. ✓ Seller declaration signed
8. ✓ Acquisition cost recorded (> 0)
9. ✓ No outstanding flags
10. ✓ Device condition grade selected
11. ✓ Clean IMEI confirmed
12. ✓ Not blacklisted
13. ✓ Activation lock removed
14. ✓ Factory reset verified
15. ✓ Data wiped verified

The `PublishingGateStatus` component shows each gate with a pass/fail state. The "Convert to Product" button is disabled until all 15 gates pass.

Gates are enforced both in the UI and server-side in the `convertIntakeToProduct` server action.

## Source of Truth After Conversion

After intake is converted to a product, the product record becomes the source of truth for active inventory and customer-facing storefront data.

The intake record remains the historical operational record.

# 9.4 Status Update Notifications

When admin marks order as `Ready for Pickup`:

- Send pickup ready email to customer.
Use the order's `customer_locale` for the customer email.

When admin marks order as `Shipped`:

- Send shipping email to customer.
Use the order's `customer_locale` for the customer email.

When admin marks order as `Cancelled`:

- REQUIRED: Send Order Cancelled email to customer in `orders.customer_locale`.
- Email must include refund notice if payment was captured.
- Email failure must not block the cancellation — log and continue.

Cancellation email is REQUIRED (not optional).

Email failures should not block the status update.

# 23. Audit and Safety Requirements

Admin audit logging is **required for MVP**, not future scope. The `admin_audit_logs` table is defined in the Database Schema Specification.

## Required MVP Audit Events

The following actions must be logged to `admin_audit_logs`:

- Order status changed (from → to, actor, timestamp)
- Order cancelled (actor, reason, timestamp)
- Product price changed (old price, new price, actor)
- Product status changed (draft → active, archived, etc.)
- Device intake created (actor, intake ID)
- Device intake status changed (actor, old status, new status)
- Seller identity recorded (actor — do NOT log the ID number itself)
- Hold period waived (actor — high-risk action, always audit)
- IMEI verification updated (actor, result)
- Testing checklist completed (actor)
- Intake converted to product (actor, intake ID, product ID)
- Warranty claim status updated (actor, old status, new status)
- Coupon created or deactivated (actor)
- Settings updated (actor, changed keys)

## Audit Log Table

```text
admin_audit_logs
```

Fields:

```text
id
actor_id (references auth.users)
actor_email
action (enum: audit_action)
table_name
record_id
old_values (jsonb)
new_values (jsonb)
ip_address
user_agent
notes
created_at
```

## Security Note

- Seller ID number must NEVER appear in `old_values` or `new_values` — only log that the field was updated
- Audit logs are append-only — no update or delete permissions
- Only admin role can view audit log entries

# 23b. Law Enforcement Data Access (RCW 19.60)

Washington State law (RCW 19.60) requires secondhand dealers to make seller identity records available to law enforcement upon request.

## Data Available for Law Enforcement

The following fields in `device_intakes` support compliance reporting:

- `seller_full_name`
- `seller_id_type`
- `seller_id_state`
- `seller_id_expiry`
- `seller_address`
- `seller_declaration_signed`
- `seller_declaration_signed_at`
- `acquisition_date`
- `imei` (device identifier)
- `serial_number`
- `hold_until_date`

**Note:** `seller_id_number_encrypted` requires decryption before it can be shared. Decryption requires the `SELLER_ID_ENCRYPTION_KEY` environment variable. This is a manual operation performed by an authorized admin — not an automated UI feature.

## MVP Approach

For MVP, law enforcement data requests are handled manually by the admin:

1. Law enforcement contacts the store
2. Admin retrieves intake record from the admin dashboard
3. Admin decrypts seller ID number using a secure admin tool (future feature — not MVP)
4. Admin provides required records in compliance with the request

A dedicated law enforcement data export UI is a future feature, not MVP.

# 24. Admin Security Rules

1. Admin routes must be server-protected.
2. Admin actions must verify role server-side.
3. Public users must not access private fields.
4. Product IMEI, serial number, and cost are admin-only.
5. Customer data should only be shown when needed for order fulfillment.
6. Service role key must stay server-only.
7. File uploads must validate file type and size.
8. Destructive actions should require confirmation.
9. Prefer archive over permanent delete.
10. Role changes should be admin-only.
11. IMEI and serial number should be visible only to staff/admin.
12. Cost and acquisition source should be visible only to staff/admin.
13. Customer locale may be visible for support but must not affect authorization.
14. Admin UI remains English-only for MVP.

15. Internal-only intake images must never appear publicly.
16. Publishing gates must be enforced server-side, not only through admin UI.
17. Warranty claim notes must be staff/admin-only.
18. Customers may view safe warranty information, but only staff/admin can update claim status or claim notes.
