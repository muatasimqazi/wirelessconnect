# 1. Purpose

This document defines the technical architecture for the Wireless Connect Online Store. It should be used by Claude Code/Codex to generate a consistent, scalable, maintainable application.

The goal is to build a low-cost custom e-commerce platform for selling used phones, tablets, laptops, and accessories online — initially in Shoreline, WA and nationwide across the U.S. — with strong used-device operations including intake, testing, IMEI verification, compliance tracking, warranty tracking, and future support for repairs and trade-ins.

# 3. Architecture Philosophy

Claude Code should follow these principles:

1. Server Components by default.
2. Client Components only when interactivity is required.
3. Server Actions for trusted writes.
4. Route Handlers for webhooks and public API endpoints.
5. Supabase service role only on the server.
6. Never expose private fields such as IMEI, serial number, cost, or admin notes to public clients.
7. Keep the MVP small and stable before adding repair/trade-in systems.
8. Treat Stripe webhooks as the source of truth for successful payments.
9. Validate every mutation using Zod.
10. Prioritize mobile performance and fast product browsing.
11. Build locale-aware routing from the beginning.
12. Never hardcode customer-facing text.
13. Resolve customer-facing content by locale with English fallback.
14. Keep admin dashboard English-only for MVP unless explicitly requested.
15. Treat device intake, testing, IMEI verification, hold period enforcement, and warranty tracking as MVP operational requirements.
16. Prevent used phones from being published until required verification gates are complete.
17. Keep intake records, IMEI, serial numbers, cost, seller identity data, and acquisition data staff/admin-only.
18. Webhook processing must be idempotent — use the `webhook_events` table to prevent duplicate order processing.
19. Use `guest_access_token` for unauthenticated order lookup — never rely on order_number or order_id alone.
20. Use Stripe Tax for automatic multi-state tax calculation — required for nationwide U.S. selling.
21. Apply HTTP security headers in Next.js config (CSP, HSTS, X-Frame-Options, etc.).
22. Apply rate limiting to auth endpoints and coupon validation.
23. Never store seller government ID numbers in plaintext — use pgp_sym_encrypt.
24. Use atomic SQL patterns for inventory decrement and coupon redemption.

# 12. Product Architecture

## Product Publishing Gate

Used phones must not be published as active products until required operational checks are complete.

Required before `status = active` for used phones:

- Clean IMEI verified
- IMEI verification status passed
- Testing status passed
- Factory reset verified
- Data wipe verified
- Activation lock removed when applicable
- Condition grade selected
- Price assigned
- Warranty days assigned
- Required customer-facing photos uploaded

Publishing gates should be enforced in server actions, not only in UI validation.

## Public Product Query

Public product queries must only return safe fields.

Do not expose:

- imei
- serial_number
- Actual IMEI values
- Actual serial numbers
- cost
- admin notes
- acquisition_source
- internal_device_notes
- intake-only images

Public storefront queries may expose verification indicators such as `is_clean_imei` and `imei_verification_status`, but must never expose actual IMEI or serial number values.

Use either:

- `public_products` database view
- Explicit field selection in server queries

## Localized Product Query

Public product queries should accept a locale parameter.

Example:

```ts
getProductBySlug(slug: string, locale: SupportedLocale)
getProducts(params: ProductQueryParams, locale: SupportedLocale)
```

Product queries should:

- Return safe public fields only.
- Resolve localized title, subtitle, description, SEO title, and SEO description.
- Fall back to English/default fields when localized content is missing.
- Never expose IMEI, serial number, cost, or admin notes.
- Expose only safe trust indicators such as clean IMEI, tested, data wiped, warranty days, and factory reset verification. Do not expose raw internal testing or IMEI review statuses publicly.

## Product Pages

Data needed:

# 13. Cart Architecture

The cart must support guests and authenticated users.

## Guest Cart

Use an anonymous cart ID stored in a secure cookie.

Cookie name:

```text
wc_cart_id
```

Locale cookie:

```text
wc_locale
```

Cart data should remain locale-independent. Product display text should be localized at render time.

Guest flow:

1. User adds product to cart.
2. Server action creates cart if needed.
3. Cart ID is stored in cookie.
4. Cart items are stored in Supabase.

## Authenticated Cart

Authenticated users use `user_id` on `carts`.

## Merge Behavior

When a guest signs in:

1. Find guest cart by cookie.
2. Find existing user cart.
3. Merge items.
4. Delete or expire guest cart.
5. Store user cart going forward.

## Cart Validation

Before creating checkout:

- Product exists
- Product is active
- Quantity is available
- Product allows selected fulfillment method
- Price is refreshed from database

# 14. Checkout Architecture

Use Stripe Checkout for MVP.

## Checkout Flow

```text
Cart
→ Checkout Page
→ Create Order Pending
→ Create Stripe Checkout Session
→ Redirect to Stripe
→ Stripe Payment
→ Webhook Confirms Payment
→ Order Confirmation Page
```

## Why Stripe Checkout

- Lower implementation complexity
- Handles card entry securely
- Supports Apple Pay/Google Pay where available
- Reduces PCI burden

## Checkout Server Action

File:

```text
features/checkout/actions.ts
```

Action:

```ts
createCheckoutSession(input)
```

Responsibilities:

1. Validate input using Zod.
2. Load cart server-side.
3. Revalidate product inventory and pricing from database.
4. Create pending order with `guest_access_token = gen_random_uuid()`.
5. Store `customer_locale` on the order.
6. Create order items snapshot (warranty_days copied from product at time of order).
7. Apply coupon atomically via single SQL UPDATE if present.
8. Create Stripe Checkout Session with Stripe Tax enabled when `stripe_tax_enabled` setting is true.
9. Add shipping insurance line item for orders over configured threshold.
10. Save `stripe_checkout_session_id` to order.
11. Return Stripe checkout URL.

# 15. Stripe Webhook Architecture

Route:

```text
app/api/stripe/webhook/route.ts
```

Webhook must verify Stripe signature using `STRIPE_WEBHOOK_SECRET`.

## Events to Handle

```text
checkout.session.completed
payment_intent.succeeded
payment_intent.payment_failed
charge.refunded
```

## checkout.session.completed

Responsibilities:

1. Insert event into `webhook_events` — if conflict (already processed), return 200 immediately.
2. Find order by `stripe_checkout_session_id`.
3. If order is already marked paid, skip and return 200.
4. Mark `payment_status = paid`.
5. Mark `status = paid`.
6. Set `paid_at`.
7. Atomically decrement inventory using `UPDATE ... WHERE quantity > 0 RETURNING id`. If returns 0 rows, flag as oversell and notify admin.
8. Create warranty records for eligible order items.
9. Clear cart.
10. Send localized order confirmation email.
11. Use `orders.customer_locale` when selecting customer email template language.
12. If pickup selected, include pickup instructions.
13. Send admin new-order notification email.

## Idempotency

Webhook handling must be idempotent. This is a hard requirement, not optional.

Never decrement inventory twice for the same order.

Implementation (required):

1. Before processing any webhook, attempt to insert the Stripe event ID into `webhook_events` using `ON CONFLICT DO NOTHING`.
2. If the insert returns 0 rows, the event was already processed — return HTTP 200 immediately without further processing.
3. If the insert succeeds, proceed with order updates, inventory decrement, and warranty creation.
4. Wrap all webhook processing in a database transaction where possible.

```ts
// Webhook idempotency check (required before any processing)
const { data: inserted } = await supabaseAdmin
  .from('webhook_events')
  .insert({ stripe_event_id: event.id, event_type: event.type, payload: event })
  .select('id')
  .single()

if (!inserted) {
  // Already processed — return 200 to Stripe
  return NextResponse.json({ received: true })
}
```

# 16. Inventory Architecture

Inventory rules:

1. Public UI should hide or disable sold-out products.
2. Cart should warn if item becomes unavailable.
3. Checkout must re-check inventory server-side.
4. Inventory decrements only after payment success.
5. Inventory never decrements on failed payment.
6. Used phones usually have quantity `1`.
7. Accessories may have quantity greater than `1`.
8. Used phones cannot become active until intake/testing/IMEI publishing gates pass.
9. Intake records are staff/admin-only and should not affect public inventory until converted to products.
10. MVP uses server-side inventory validation before Stripe Checkout and after confirmed payment.
11. Full inventory reservations with expiration are future scope unless explicitly requested.


Functions:

# 18. Order Architecture

## Order Creation

Orders are created before Stripe redirect with:

```text
status = pending
payment_status = unpaid
```

After payment:

```text
status = paid
payment_status = paid
```

## Order Number

Use format:

```text
WC-10001
```

Generated server-side using a database sequence or utility function.

## Order Confirmation

Route:

```text
/order-confirmation?token=<guest_access_token>
```

For guest orders:

- Order confirmation page must require a `guest_access_token` — a UUID stored on the order and sent to the customer via confirmation email or URL redirect.
- Never expose orders via `/order-confirmation?order=WC-10001` alone. Any user who guesses an order number would be able to view another customer's order (IDOR vulnerability).
- Authenticated users who land on the confirmation page can have their `user_id` verified via session.
- The `guest_access_token` is generated as a UUID when the order is created and is single-purpose.

Guest order lookup pattern:

```ts
// Only return order if token matches — prevents IDOR
const { data: order } = await supabase
  .from('orders')
  .select('...')
  .eq('guest_access_token', token)
  .single()
```

## Warranty Creation

After successful payment, eligible order items should create warranty records.

Warranty records should snapshot:

- Order ID
- Order item ID
- Product ID
- Customer information
- Customer locale
- Product title
- Device brand/model
- Serial number and IMEI for staff/admin support
- Warranty start date
- Warranty expiration date

Warranty duration must be based on the order item snapshot, not the current product record.

## Supabase Auth Email Configuration

Supabase Auth sends password reset and magic link emails using its own internal system by default.

To route these through Resend:

1. Configure a custom SMTP provider in the Supabase dashboard (Settings → Auth → SMTP).
2. Point it to Resend's SMTP endpoint.
3. Use a custom email template inside Supabase Auth settings to match Wireless Connect's branding.

Do NOT implement a custom password reset email via Resend — use the Supabase Auth SMTP configuration. Implementing a separate password reset flow from scratch bypasses Supabase Auth's built-in secure token handling.

## Email Sending Rules

- Send order confirmation only after Stripe webhook confirms payment.
- Do not send confirmation from the client.
- Email failures should not fail the order.
- Log email errors server-side.
- Use `orders.customer_locale` for customer-facing emails.
- Fall back to English when a localized template is unavailable.
- Include `guest_access_token`-based order URL in order confirmation emails for guest orders.

# 31. Security Requirements

1. Enable RLS on all Supabase tables.
2. Never expose service role key to browser.
3. Never expose IMEI, serial number, cost, or acquisition data on public pages.
4. Verify Stripe webhook signatures using `STRIPE_WEBHOOK_SECRET`.
5. Validate all server actions with Zod on both client and server.
6. Use server-side authorization checks for admin routes — do not rely on middleware alone.
7. Do not store card details. Stripe handles all payment data.
8. Sanitize user-generated content before display.
9. Use httpOnly secure cookies for cart ID and locale.
10. Protect admin file uploads with signed URLs or server-side proxy.
11. Keep intake records staff/admin-only.
12. Keep internal-only images private in the `device-intake-images` bucket.
13. Keep warranty IMEI/serial number fields staff/admin-only.
14. Enforce publishing gates server-side — never rely on UI-only validation.
15. Public storefront must show only IMEI verification indicators, never actual IMEI values.
16. Customers may view safe warranty information (status, expiry), but cannot update claim status or notes.
17. Use a role-protection trigger in the database to prevent client-side role escalation.
18. Configure HTTP security headers in `next.config.js`:
    - `Content-Security-Policy` (CSP)
    - `Strict-Transport-Security` (HSTS)
    - `X-Frame-Options: DENY`
    - `X-Content-Type-Options: nosniff`
    - `Referrer-Policy: strict-origin-when-cross-origin`
    - `Permissions-Policy`
19. Apply rate limiting to auth endpoints (sign-in, sign-up, password reset) and coupon validation.
20. Encrypt seller government ID numbers using `pgp_sym_encrypt` — never store or log plaintext.
21. Use `guest_access_token` on orders to prevent IDOR on order confirmation pages.
22. Use atomic SQL for inventory decrement and coupon redemption to prevent race conditions.
23. Use `webhook_events` table to prevent duplicate webhook processing.
24. Log admin actions (role changes, product status changes, order updates) to `admin_audit_logs`.
25. Do not log or expose the `SELLER_ID_ENCRYPTION_KEY` or `SUPABASE_SERVICE_ROLE_KEY` in any output.

## HTTP Security Headers (next.config.js)

```js
const securityHeaders = [
  { key: 'X-DNS-Prefetch-Control', value: 'on' },
  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
```

# 32. Nationwide Compliance Architecture

Wireless Connect sells to customers anywhere in the U.S. The following compliance requirements apply.

## Multi-State Sales Tax

Use Stripe Tax to automatically calculate and collect sales tax for all U.S. states.

Configuration:

1. Enable Stripe Tax in the Stripe dashboard.
2. Register your tax ID and nexus locations in Stripe.
3. Pass `automatic_tax: { enabled: true }` when creating Stripe Checkout Sessions.
4. Store `stripe_tax_calculation_id` on the order for audit and reconciliation.
5. Monitor Stripe Tax reports for filing in states where economic nexus thresholds are met.

Economic nexus thresholds vary by state — most states trigger at $100,000 in sales or 200 transactions per year (per South Dakota v. Wayfair).

## Secondhand Dealer Compliance

Washington State RCW 19.60 (and similar laws in other states) requires secondhand dealers to:

- Record seller government-issued ID before purchasing devices.
- Record IMEI and serial number for each device.
- Hold devices for a minimum period (5 days in WA) before resale.
- Make records available to law enforcement upon request.

Implementation:

- Store seller identity fields on `device_intakes` (see Database Schema).
- Encrypt `seller_id_number_encrypted` using `pgp_sym_encrypt` with `SELLER_ID_ENCRYPTION_KEY`.
- Set `hold_until_date = acquisition_date + hold_period_days`.
- Enforce hold period via a database trigger that prevents `status = 'ready_to_list'` before hold expires.
- Admin dashboard must display hold period status and unlock date for each intake.

## Shipping Compliance

For nationwide orders:

- Lithium battery shipping: follow USPS, UPS, and FedEx hazmat regulations for devices containing lithium-ion batteries.
- Signature confirmation: require signature for orders over $500 (configurable via settings).
- Use `shipping_signature_threshold` as the canonical settings key for signature confirmation.
- Shipping insurance: add insurance for orders over $200 (configurable via settings).
- Declare accurate declared value when purchasing insurance through carrier.

## Privacy (CCPA)

When selling to California customers, California Consumer Privacy Act (CCPA) obligations apply.

Required:

- Privacy Policy must include CCPA-specific language.
- "Do Not Sell My Personal Information" link in footer (even if Wireless Connect does not sell data, the link satisfies compliance and discloses the policy).
- Provide a process for California residents to request data deletion within 45 days.
- `submitDataDeletionRequest` server action should insert into `data_deletion_requests`; actual deletion is a staff-fulfilled manual process for MVP.

## OFAC Screening (International — Future)

Before enabling sales outside the United States:

- Implement OFAC (Office of Foreign Assets Control) sanctions screening before completing any international order.
- Do not ship to embargoed countries or sanctioned individuals.
- This is blocked at the product requirement level until explicitly enabled.
