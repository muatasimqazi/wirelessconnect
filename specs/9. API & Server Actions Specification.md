# 1. Purpose

This document defines the server actions, route handlers, validation schemas, and integration boundaries for the Wireless Connect Online Store.

Claude Code should use this document as the source of truth for naming, responsibilities, inputs, outputs, and security rules.

---

# 2. Implementation Principles

1. Use Server Actions for trusted mutations.
2. Use Route Handlers for webhooks and external HTTP integrations.
3. Use Server Components for initial data fetching when possible.
4. Validate all inputs with Zod.
5. Never trust client-provided price, inventory, role, or payment data.
6. Use Supabase RLS for customer-facing access.
7. Use Supabase service role only in trusted server-side code.
8. Never expose IMEI, serial number, cost, or admin notes publicly.
9. Use Stripe webhooks as the payment source of truth.
10. Make payment and inventory actions idempotent — use `webhook_events` table to prevent duplicate processing.
11. All customer-facing actions must be locale-aware.
12. Customer-facing messages should use translation keys or localized strings.
13. Public product/category queries should resolve localized content with English fallback.
14. Store customer locale on orders for localized email delivery.
15. Keep admin-facing actions English-only for MVP unless explicitly requested.
16. Apply rate limiting to auth actions and public coupon validation.
17. Use atomic SQL for inventory decrement and coupon redemption — never check-then-update in separate queries.
18. Use `guest_access_token` for unauthenticated order lookups — never order_id or order_number alone.
19. Validate locale against `supported_locales` in settings — never hardcode locale values in action logic.
20. Encrypt seller government ID with `pgp_sym_encrypt` — never store or log plaintext ID numbers.
21. Log admin actions (role changes, product status, order status, warranty claim status) to `admin_audit_logs`.

# 3. Standard Server Action Response

All server actions should return a consistent shape.

```ts
export type ActionResult<T = unknown> = {
  success: boolean
  message?: string
  data?: T
  fieldErrors?: Record<string, string[]>
}
```

## Success Example

```ts
{
  success: true,
  message: "Product created successfully.",
  data: product
}
```

## Error Example

```ts
{
  success: false,
  message: "Could not save product.",
  fieldErrors: {
    title: ["Title is required."]
  }
}
```

# 4. Shared Localization Types

Supported MVP locales:

```ts
export type SupportedLocale = "en" | "es"
```

Customer-facing actions should accept or derive locale from:

1. Route segment
2. `wc_locale` cookie
3. Authenticated user's `profiles.preferred_locale`
4. English fallback

Use English as the fallback when a localized value is unavailable.

## `createCheckoutSession`

```ts
createCheckoutSession(input: CreateCheckoutSessionInput): Promise<ActionResult<{ url: string }>>
```

### Input

```ts
type CreateCheckoutSessionInput = {
  cartId?: string
  customerEmail: string
  customerName: string
  customerPhone?: string
  fulfillmentMethod: "pickup" | "shipping"
  shippingAddress?: AddressInput
  billingAddress?: AddressInput
  couponCode?: string
  customerLocale?: SupportedLocale
}
```

### Responsibilities

1. Validate input with Zod.
2. Apply rate limiting — max 10 checkout attempts per 5 minutes per IP.
3. Load cart server-side.
4. Validate cart is not empty.
5. Re-fetch product prices from database.
6. Validate inventory for all cart items.
7. Validate fulfillment method is supported by all cart products.
8. Apply coupon atomically if provided (single SQL UPDATE returning discount amount).
9. Calculate subtotal, discount, shipping total, and total (tax calculated by Stripe).
10. Generate `guest_access_token = gen_random_uuid()`.
11. Create pending order with `guest_access_token`.
12. Store `customer_locale` on the order.
13. Create order item snapshots (warranty_days from product at time of order).
14. Create Stripe Checkout Session with `automatic_tax: { enabled: true }` when stripe_tax_enabled.
15. Add shipping insurance as Stripe line item when order exceeds insurance threshold.
16. Save `stripe_checkout_session_id` to order.
17. Return Stripe checkout URL.

### Security Rules

- Never use client-provided product price.
- Never decrement inventory here.
- Inventory decrements only after payment webhook.
- Validate locale against supported locales.
- Use locale for order records and later email templates, not for pricing logic.

## `POST /api/stripe/webhook`

### Responsibilities

- Verify Stripe webhook signature using `STRIPE_WEBHOOK_SECRET`.
- Insert event into `webhook_events` using `ON CONFLICT DO NOTHING` — if 0 rows returned, event already processed; return 200 immediately.
- Handle allowed Stripe events.
- Update order/payment status.
- Decrement inventory atomically after payment success using `UPDATE ... WHERE quantity > 0 RETURNING id`.
- Create warranty records for eligible order items.
- Send localized confirmation email using `orders.customer_locale`.
- Send admin new-order notification.
- Clear cart.
- On any unrecoverable error, log to server; still return 200 to Stripe to prevent infinite retries.

### Events

```text
checkout.session.completed
payment_intent.succeeded
payment_intent.payment_failed
charge.refunded
```

---

## `handleCheckoutSessionCompleted`

```ts
handleCheckoutSessionCompleted(session: Stripe.Checkout.Session): Promise<void>
```

### Responsibilities

- Find order by `stripe_checkout_session_id`.
- If order payment_status is already `paid`, exit safely (idempotency guard).
- Mark order `payment_status = paid`, `status = paid`.
- Set `paid_at = now()`.
- Store `stripe_tax_calculation_id` from Stripe session.
- Store tax jurisdiction from Stripe session if available.
- Atomically decrement inventory: `UPDATE products SET quantity = quantity - 1 WHERE id = $id AND quantity > 0 RETURNING id`. If 0 rows returned, flag as potential oversell; notify admin.
- Create warranty records for eligible order items (warranty_days from order_items snapshot).
- Send localized order confirmation email using `orders.customer_locale`.
- Include `guest_access_token` URL in confirmation email for guest orders.
- Send admin new order notification email.
- Clear cart using cart ID if known.

---

```text
pending → paid (via webhook only)
paid → processing
paid → cancelled
processing → ready_for_pickup (pickup orders only)
processing → shipped (shipping orders only)
ready_for_pickup → picked_up
shipped → delivered
```

Invalid or skipped transitions must be rejected.

## `validateCoupon`

```ts
validateCoupon(
  code: string,
  subtotal: number
): Promise<ActionResult<CouponValidationResult>>
```

### Access

- Public server action.
- Rate limited: max 20 attempts per 15 minutes per IP.

### Responsibilities

- Check coupon exists and is active.
- Check usage limits.
- Check start/end dates.
- Check minimum order amount against provided subtotal.
- Return discount type and calculated discount amount.
- Do NOT increment `used_count` here — only increment at checkout via atomic SQL.

### Atomic Coupon Redemption (at checkout, not validation)

When applying coupon at checkout:

```sql
UPDATE public.coupons
SET used_count = used_count + 1
WHERE code = $1
  AND active = true
  AND (usage_limit IS NULL OR used_count < usage_limit)
  AND (starts_at IS NULL OR starts_at <= now())
  AND (expires_at IS NULL OR expires_at > now())
RETURNING id, type, value, minimum_order_amount;
```

If 0 rows returned, coupon is no longer valid — abort checkout with error message.

Rules:

- Must be idempotent — use `webhook_events` table to prevent double-decrement.
- Must use atomic SQL to prevent oversell:

```sql
UPDATE public.products
SET quantity = quantity - 1
WHERE id = $productId
  AND quantity > 0
  AND status = 'active'
RETURNING id, quantity;
```

- If the UPDATE returns 0 rows, product quantity was already 0 — flag as potential oversell and alert admin.
- Do NOT manually check quantity then decrement in two steps.

# 21. Security Rules

1. All admin actions must call `requireStaff()` or `requireAdmin()`.
2. Customer actions must verify ownership.
3. Public product queries must exclude private fields and use the `public_products` view or equivalent.
4. Customer order item queries must use `customer_order_items` view — never the base `order_items` table.
5. Cart actions must verify cart ownership or guest cookie.
6. Checkout must recalculate all prices server-side — never trust client prices.
7. Stripe webhook must verify signature.
8. Webhook idempotency must be enforced via `webhook_events` table.
9. Inventory must decrement only once per paid order using atomic SQL.
10. Service role key must never be imported into client code.
11. Admin notes must never be returned to customer queries.
12. IMEI, serial number, and cost must never appear in public responses.
13. `guest_access_token` must be used for all guest order lookups — never order_id or order_number alone.
14. Locale values must be validated against `supported_locales` setting at application layer.
15. Public localized product responses may include translations but must not include private fields.
16. Customer locale must not affect pricing, tax, or authorization logic.
17. Coupon `used_count` must only be incremented atomically via single SQL UPDATE.
18. Seller ID numbers must be encrypted with `pgp_sym_encrypt` — never stored or logged in plaintext.
19. Rate limiting must be applied to `signInWithPassword`, `signUpWithPassword`, and `validateCoupon`.
20. Admin actions involving sensitive data (role changes, status changes) must be logged to `admin_audit_logs`.
21. Warranty IMEI and serial number must never be returned to customer-facing warranty queries.
22. Admin UI may remain English-only for MVP.

# 24. Acceptance Criteria

This API and Server Actions Specification is implemented when:

1. All MVP server actions exist.
2. All actions use Zod validation.
3. All actions return `ActionResult`.
4. Admin actions are role-protected.
5. Customer actions verify ownership.
6. Public queries exclude private fields.
7. Checkout recalculates prices server-side.
8. Stripe webhook verifies signatures.
9. Inventory decrements only after payment success.
10. Webhook handling is idempotent.
11. Emails are sent from server-side only.
12. Sensitive keys are never exposed to the browser.
13. Route handlers are limited to webhooks/search/external integrations.
14. Server actions follow consistent file organization.
15. Post-MVP actions are not implemented during MVP unless requested.
16. Customer-facing product queries accept or derive locale.
17. Product/category responses resolve localized content with English fallback.
18. Checkout stores customer locale on the order.
19. Customer-facing emails use order/customer locale.
20. Search route accepts locale and returns localized display fields where available.
21. Preferred locale can be updated for authenticated users.
22. Guest locale can be persisted in `wc_locale` cookie.
23. Locale values are validated with Zod.
24. Admin actions remain protected and English-only for MVP.
25. Webhook idempotency enforced via `webhook_events` table.
26. Inventory decremented atomically — no oversell on concurrent checkouts.
27. Coupon redemption is atomic — no race condition on `used_count`.
28. Guest order lookup requires `guest_access_token` — IDOR prevention verified.
29. Warranty claims can be submitted by authenticated customers for their own active warranties.
30. Device intake actions enforce hold period gate before product listing.
31. IMEI verification records the service used (not just the result).
32. Data deletion requests are logged and responded to within 45 days.
33. Data deletion requests are stored in `data_deletion_requests`.
34. Customer cancellation requests are stored in `order_cancellation_requests` and never cancel an order automatically.
35. Warranty claim images upload to a private bucket and are scoped to the owning warranty.
36. Used-phone active publishing enforces all 15 canonical publishing gates, including 6 customer-facing images.
