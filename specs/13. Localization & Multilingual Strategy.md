# 1. Purpose

This document defines the multilingual, localization, and accessibility strategy for the Wireless Connect Online Store.

The goal is to make the website usable by customers with limited English proficiency while maintaining a simple and trustworthy shopping experience.

Wireless Connect serves customers:

- Locally in Shoreline, WA and North Seattle
- Nationwide across all U.S. states and territories (online orders)
- Globally in the future

Many customers may prefer shopping in languages other than English.

# 5. Localization Principles

## Principles

1. Never hardcode customer-facing text.
2. Every customer-facing string must be translatable.
3. Use plain language.
4. Use icons where helpful.
5. Avoid technical jargon.
6. Use translation keys instead of inline text.
7. Keep English as the source language.
8. Use logical CSS properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) — never directional CSS — to support RTL without layout rewrites.
9. All legal pages (Terms of Service, Privacy Policy, Returns, Warranty, Shipping) must be translated for MVP (English + Spanish).
10. Admin-facing UI remains English only. Localization applies to customer-facing surfaces only.

## RTL Architecture Note

RTL support must be designed into the codebase from Sprint 1, even though Arabic is not an MVP language.

Required from day one:

- Use `dir` attribute on the `<html>` element, driven by locale config
- Use logical CSS properties throughout (not `left`/`right`)
- Configure `next-intl` locale metadata to include `direction: 'rtl'` for Arabic, Dari, Pashto, Urdu
- Test layouts in RTL mode during development even before Arabic is added

Example next-intl locale config:

```ts
export const locales = ['en', 'es'] as const
export type Locale = typeof locales[number]

export const localeConfig = {
  en: { direction: 'ltr', label: 'English' },
  es: { direction: 'ltr', label: 'Español' },
  // Future:
  // ar: { direction: 'rtl', label: 'العربية' },
}
```

## IMEI — Important Distinction

The IMEI field in Section 13 (Accessibility Through Language) displays a plain-language **tooltip explanation** of the IMEI term — not the device's actual IMEI number.

The actual IMEI value:

- Is stored securely in the database
- Is never exposed to customers in any UI or email
- Is used internally for verification and compliance only
- Is excluded from `public_products` view and `customer_order_items` view

The tooltip translation is for term education only:

English:

```text
Unique phone identifier used to verify activation eligibility.
```

Spanish:

```text
Identificador único utilizado para verificar la activación del teléfono.
```

This tooltip explains what IMEI means — it does not display the device's IMEI.

# 15. Timezone Handling

## Nationwide Customer Context

Wireless Connect now ships to customers across all U.S. time zones (Pacific, Mountain, Central, Eastern, Alaska, Hawaii).

## Rules

1. All timestamps stored in the database must be in UTC.
2. All timestamps displayed to customers must be converted to their local timezone.
3. For orders, use the shipping address state to infer timezone for display purposes (best effort).
4. Store hours are displayed in Pacific Time (PT) — the store's local timezone.
5. Order confirmation and email timestamps display in PT with the timezone label:

```text
Ordered: May 25, 2026 at 2:34 PM PT
```

6. Admin dashboard displays all timestamps in PT by default, with UTC available on hover.
7. Do not assume customers are in Pacific Time — display-only timezone inference is acceptable for UX, but all backend logic operates in UTC.

## Implementation

- Use `Intl.DateTimeFormat` for client-side timezone display
- Store `timeZone` in the customer's browser where needed
- Do not store customer timezone in the database — derive it from display context

# 22. Acceptance Criteria

Localization strategy is complete when:

1. English and Spanish are supported for all customer-facing UI.
2. Customer-facing text is fully translatable — no hardcoded strings.
3. Locale-aware routing exists (`/en`, `/es`).
4. Language switcher works globally on desktop and mobile.
5. Customer locale is persisted (logged-in: `profiles.preferred_locale`, guest: cookie).
6. All MVP transactional emails are sent in the customer's `customer_locale`.
7. Technical phone terminology includes plain-language tooltip explanations in English and Spanish.
8. WhatsApp contact options are available and translated.
9. SEO supports multiple languages with hreflang tags.
10. The architecture supports future RTL languages without major layout rewrites (logical CSS properties used throughout).
11. Mobile and desktop experiences are fully localized.
12. English remains the fallback language.
13. All legal pages (Terms, Privacy, Returns, Warranty, Shipping) are translated into Spanish for MVP.
14. CCPA "Do Not Sell" link is translated into Spanish in the footer.
15. IMEI tooltips display term explanations only — no actual IMEI values are exposed in any customer-facing surface.
16. All database timestamps are stored in UTC; customer-facing timestamps display in Pacific Time.
17. Warranty claim emails are sent in `warranties.customer_locale`.
18. Order cancelled email is sent in `orders.customer_locale`.
19. Admin-facing UI remains English only.
20. Guest order confirmation link (`/[locale]/order-confirmation?token=...`) respects the customer's locale.
