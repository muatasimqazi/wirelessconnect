# 1. Purpose

This document defines the technical architecture for the Wireless Connect Online Store. It should be used by Claude Code/Codex to generate a consistent, scalable, maintainable application.

The goal is to build a low-cost custom e-commerce platform for selling used phones, tablets, laptops, and accessories online, with strong used-device operations including intake, testing, IMEI verification, warranty tracking, and future support for repairs and trade-ins.

# 3. Architecture Philosophy

Claude Code should follow these principles:

1. Server Components by default.
2. Client Components only when interactivity is required.
3. Server Actions for trusted writes.
4. Route Handlers for webhooks and public API endpoints.
5. Supabase service role only on the server.
6. Never expose private fields such as IMEI, serial number, cost, or admin notes to public clients.
7. Keep the MVP small and stable before adding repair/trade-in systems.
8. Treat Stripe webhooks as the source of truth for successful payments.
9. Validate every mutation using Zod.
10. Prioritize mobile performance and fast product browsing.
11. Build locale-aware routing from the beginning.
12. Never hardcode customer-facing text.
13. Resolve customer-facing content by locale with English fallback.
14. Keep admin dashboard English-only for MVP unless explicitly requested.
15. Treat device intake, testing, IMEI verification, and warranty tracking as MVP operational requirements.
16. Prevent used phones from being published until required verification gates are complete.
17. Keep intake records, IMEI, serial numbers, cost, and acquisition data staff/admin-only.

# 5. Route Groups

## Storefront Routes

```text

```

These are public or customer-facing routes.

Examples:

```text

/es/shop
/en/products/[slug]
/es/products/[slug]
```

```text
app/admin/...
```

These require staff/admin authorization.

Examples:

```text
/admin/intake
/admin/intake/new
/admin/products
/admin/orders
/admin/warranties
```

```text
app/[locale]/auth/...
```

Examples:

```text

```

```text

```

Use route handlers only for cases that require HTTP endpoints:

- Stripe webhooks

# 6. Rendering Strategy

## Server Components

Use Server Components for:

- Home page
- Product listing page
- Product detail page
- Category pages
- Account pages where possible
- Admin pages where data can be fetched server-side

## Client Components

Use Client Components for:

- Cart drawer
- Add to cart button
- Search overlay
- Product image gallery
- Filter drawer on mobile
- Checkout form
- Admin forms
- Repair/trade-in wizards

## Static vs Dynamic

### Static or ISR candidates

- Home page
- Category pages
- Product detail pages

### Dynamic routes

- Cart
- Checkout
- Account
- Admin
- Order confirmation

Product inventory and pricing must be checked dynamically before checkout even if product pages are cached.

## Locale-Aware Rendering

Storefront pages must receive the active locale from the `[locale]` route segment.

Customer-facing Server Components should:

- Load translation messages for the active locale.
- Resolve localized product/category content with English fallback.
- Generate locale-specific metadata.

Admin routes do not require localization for MVP.

# 7. Supabase Client Strategy

Create three Supabase clients.

## Browser Client

File:

```text
lib/supabase/client.ts
```

Purpose:

- Used inside Client Components.
- Uses public anon key only.
- Must respect RLS.

## Server Client

File:

```text
lib/supabase/server.ts
```

Purpose:

- Used in Server Components and Server Actions.
- Uses cookies for authenticated user context.
- Must respect RLS.

## Admin Client

File:

```text
lib/supabase/admin.ts
```

Purpose:

- Used only in trusted server code.
- Uses service role key.
- Bypasses RLS.
- Must never be imported into Client Components.

Allowed use cases:

- Admin inventory operations
- Device intake operations
- IMEI verification and testing workflow updates
- Stripe webhook order updates
- Inventory decrement after payment
- Creating warranty records
- Warranty support operations
- Staff-only operations

# 12. Product Architecture

## Product Publishing Gate

Used phones must not be published as active products until required operational checks are complete.

Required before `status = active` for used phones:

- Clean IMEI verified
- IMEI verification status passed
- Testing status passed
- Factory reset verified
- Data wipe verified
- Activation lock removed when applicable
- Condition grade selected
- Price assigned
- Warranty days assigned
- Required customer-facing photos uploaded

Publishing gates should be enforced in server actions, not only in UI validation.

## Public Product Query

Public product queries must only return safe fields.

Do not expose:

- imei
- serial_number
- Actual IMEI values
- Actual serial numbers
- cost
- admin notes
- acquisition_source
- internal_device_notes
- intake-only images

Public storefront queries may expose verification indicators such as `is_clean_imei` and `imei_verification_status`, but must never expose actual IMEI or serial number values.

Use either:

- `public_products` database view
- Explicit field selection in server queries

## Localized Product Query

Public product queries should accept a locale parameter.

Example:

```ts
getProductBySlug(slug: string, locale: SupportedLocale)
getProducts(params: ProductQueryParams, locale: SupportedLocale)
```

Product queries should:

- Return safe public fields only.
- Resolve localized title, subtitle, description, SEO title, and SEO description.
- Fall back to English/default fields when localized content is missing.
- Never expose IMEI, serial number, cost, or admin notes.
- Expose only safe trust indicators such as testing status, clean IMEI status, warranty days, and factory reset verification.

## Product Pages

Route:

```text
/products/[slug]
```

Data needed:

- Product safe fields
- Product images
- Category
- Related products

## Product Listing Page

Route:

```text
/shop
/shop/[category]
```

Supports:

- Search
- Brand filter
- Storage filter
- Carrier filter
- Condition filter
- Price filter
- Sort order

Recommended sort options:

```text

Price: Low to High
Price: High to Low
Best Condition
```

# 13. Cart Architecture

The cart must support guests and authenticated users.

## Guest Cart

Use an anonymous cart ID stored in a secure cookie.

Cookie name:

```text
wc_cart_id
```

Locale cookie:

```text
wc_locale
```

Cart data should remain locale-independent. Product display text should be localized at render time.

Guest flow:

1. User adds product to cart.
2. Server action creates cart if needed.
3. Cart ID is stored in cookie.
4. Cart items are stored in Supabase.

## Authenticated Cart

Authenticated users use `user_id` on `carts`.

## Merge Behavior

When a guest signs in:

1. Find guest cart by cookie.
2. Find existing user cart.
3. Merge items.
4. Delete or expire guest cart.
5. Store user cart going forward.

## Cart Validation

Before creating checkout:

- Product exists
- Product is active
- Quantity is available
- Product allows selected fulfillment method
- Price is refreshed from database

# 14. Checkout Architecture

Use Stripe Checkout for MVP.

## Checkout Flow

```text
Cart
→ Checkout Page
→ Create Order Pending
→ Create Stripe Checkout Session
→ Redirect to Stripe
→ Stripe Payment
→ Webhook Confirms Payment
→ Order Confirmation Page
```

## Why Stripe Checkout

- Lower implementation complexity
- Handles card entry securely
- Supports Apple Pay/Google Pay where available
- Reduces PCI burden

## Checkout Server Action

File:

```text
features/checkout/actions.ts
```

Action:

```ts
createCheckoutSession(input)
```

Responsibilities:

1. Validate input using Zod.
2. Load cart server-side.
3. Revalidate product inventory and pricing.
4. Create pending order.
5. Store `customer_locale` on the order.
6. Create order items snapshot.
7. Snapshot warranty days and safe product fulfillment data.
8. Create Stripe Checkout Session.
9. Save `stripe_checkout_session_id` to order.
10. Return checkout URL.

# 15. Stripe Webhook Architecture

Route:

```text
app/api/stripe/webhook/route.ts
```

Webhook must verify Stripe signature using `STRIPE_WEBHOOK_SECRET`.

## Events to Handle

```text
checkout.session.completed
payment_intent.succeeded
payment_intent.payment_failed
charge.refunded
```

## checkout.session.completed

Responsibilities:

1. Find order by `stripe_checkout_session_id`.
2. Check if order is already marked paid.
3. Mark `payment_status = paid`.
4. Mark `status = paid`.
5. Set `paid_at`.
6. Decrement inventory.
7. Create warranty records for eligible order items.
8. Clear cart.
9. Send order confirmation email.
10. Use `orders.customer_locale` when selecting customer email template language.
11. If pickup selected, include pickup instructions.

## Idempotency

Webhook handling must be idempotent.

Never decrement inventory twice for the same order.

Implementation options:

- Check existing order payment status before updates.
- Add future `webhook_events` table if needed.

# 16. Inventory Architecture

Inventory rules:

1. Public UI should hide or disable sold-out products.
2. Cart should warn if item becomes unavailable.
3. Checkout must re-check inventory server-side.
4. Inventory decrements only after payment success.
5. Inventory never decrements on failed payment.
6. Used phones usually have quantity `1`.
7. Accessories may have quantity greater than `1`.
8. Used phones cannot become active until intake/testing/IMEI publishing gates pass.
9. Intake records are staff/admin-only and should not affect public inventory until converted to products.
10. MVP uses server-side inventory validation before Stripe Checkout and after confirmed payment.
11. Full inventory reservations with expiration are future scope unless explicitly requested.

Recommended helper:

```text
lib/utils/inventory.ts
```

Functions:

```ts
validateCartInventory(cartItems)
decrementInventory(orderItems)
markSoldOutProducts()
```

# 17. Device Intake Architecture

Device intake is an MVP admin workflow used to prepare used phones before public listing.

## Intake Routes

```text
/admin/intake
/admin/intake/new
/admin/intake/[id]
```

## Feature Files

```text
features/intake/actions.ts
features/intake/queries.ts
features/intake/schemas.ts
features/intake/types.ts
```

## Responsibilities

The intake workflow should support:

- Creating intake records
- Recording device identity
- Recording acquisition source and cost
- Recording IMEI verification result
- Recording testing checklist results
- Uploading intake images
- Marking images as internal-only
- Recording condition grade
- Preparing pricing and warranty fields
- Converting completed intake records into product listings
- Rejecting devices that should not be listed

## Publishing Gate

`convertIntakeToProduct()` should only allow conversion to active product when required checks pass.

Allowed behavior:

- Convert incomplete intake into draft product.
- Convert complete intake into active product only when publishing gates pass.

## Source of Truth After Conversion

After an intake record is converted:

- `device_intakes` remains the historical operational record.
- `products` becomes the source of truth for active inventory, pricing, availability, and customer-facing storefront data.

## Security

Intake records must be staff/admin-only.

Never expose publicly:

- IMEI
- Serial number
- Acquisition source
- Cost
- Internal notes
- Internal-only images


After payment:

```text

```

## Order Number

Use format:

```text

```

Generated server-side using a database sequence or utility function.

## Order Confirmation

Route:

```text
/order-confirmation?order=WC-10001
```

For guest orders:

- Show confirmation immediately after successful payment.
- Avoid exposing sensitive order details without verification.
- Consider using a secure token in future.

## Warranty Creation

After successful payment, eligible order items should create warranty records.

Warranty records should snapshot:

- Order ID
- Order item ID
- Product ID
- Customer information
- Customer locale
- Product title
- Device brand/model
- Serial number and IMEI for staff/admin support
- Warranty start date
- Warranty expiration date

Warranty duration must be based on the order item snapshot, not the current product record.

# 24. Middleware Architecture

Middleware should handle Supabase session refresh only.

File:

```text
middleware.ts
```

Responsibilities:

- Refresh Supabase auth session.
- Validate and normalize locale route segments.
- Avoid heavy logic.
- Avoid unnecessary matching for static assets.

Recommended matcher:

```ts
export const config = {
  matcher: [
    '/((?!_next/static|_next/image|favicon.ico|robots.txt|sitemap.xml|manifest.json|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico|css|js)$).*)',
  ],
}
```

Middleware should not perform admin authorization.

Middleware may redirect `/` to the default or detected locale, for example `/en`.

Admin authorization should not be handled in middleware. Use server-side checks in `app/admin/layout.tsx`.

# 31. Security Requirements

1. Enable RLS on all Supabase tables.
2. Never expose service role key to browser.
3. Never expose IMEI, serial number, or cost on public pages.
4. Verify Stripe webhook signatures.
5. Validate all server actions with Zod.
6. Use server-side authorization checks for admin routes.
7. Do not store card details.
8. Sanitize user-generated content.
9. Use secure cookies for cart ID.
10. Protect admin file uploads.
11. Keep intake records staff/admin-only.
12. Keep internal-only images private.
13. Keep warranty IMEI/serial number fields staff/admin-only unless explicitly required for customer support.
14. Enforce publishing gates server-side.
15. Public storefront must show only IMEI verification indicators, never actual IMEI values.
16. Customers may view safe warranty information for their own warranties, but cannot update warranty claim status or claim notes.
